# 协议类设计

## 1. 本节要解决什么问题

本节要解决的问题是：如何用 C++ 类把串口协议解析逻辑封装起来，让协议代码边界更清楚。

在 C 语言里，我们通常用全局缓冲区、状态变量和函数来解析协议。这样能工作，但项目变大后，`rxBuffer`、`rxIndex`、状态机、校验函数、命令处理容易混在一起。C++ 的价值不是“语法更高级”，而是可以把协议解析器封装成一个对象：外部只负责喂字节，内部维护状态，解析成功后输出一帧结果。

协议类适合放在 RS485 自定义协议、Modbus RTU 从机、Qt 上位机协议解析等场景里。

## 2. 基本概念

协议类可以理解为“协议解析器对象”。它通常包含：

| 成员 | 作用 |
|---|---|
| 接收缓冲区 | 保存已经收到但尚未处理完的字节 |
| 解析状态 | 表示当前在等帧头、长度、数据区还是校验 |
| 输入接口 | 每收到一个字节调用一次 |
| 输出接口 | 判断是否已经得到完整帧 |
| 校验函数 | 检查累加和或 CRC 是否正确 |
| 复位函数 | 错帧、超时或处理完成后回到初始状态 |

设计协议类时要控制边界：类负责解析协议，不负责直接操作硬件引脚；硬件收发由串口驱动层或设备类负责。

## 3. 工程用途

协议类的工程价值是减少混乱。比如一个 RS485 项目里，串口中断收到字节后，只需要调用 `parser.input(byte)`；主循环或任务发现 `parser.hasFrame()` 后，再取出完整帧处理。

这样可以把项目分成三层：

```text
串口驱动层 -> 协议解析类 -> 业务处理层
```

面试时，这种分层比“我在 while 循环里判断字符串”更有说服力。它说明你知道通信项目不是只收发字节，还要考虑缓冲区、错帧、超时、校验和模块边界。

## 4. 简单代码或伪代码

下面示例演示一个简化的自定义协议类，不依赖具体芯片库。

```cpp
#include <stdint.h>

class SimpleProtocolParser {
public:
    enum Result {
        RESULT_NONE = 0,
        RESULT_FRAME_OK,
        RESULT_FRAME_ERROR
    };

    SimpleProtocolParser()
    {
        reset();
    }

    Result input(uint8_t byte)
    {
        if (index >= sizeof(buffer)) {
            reset();
            return RESULT_FRAME_ERROR;
        }

        if (index == 0 && byte != '$') {
            return RESULT_NONE;
        }

        buffer[index++] = byte;

        if (byte == '#') {
            frameReady = true;
            return RESULT_FRAME_OK;
        }

        return RESULT_NONE;
    }

    bool hasFrame() const
    {
        return frameReady;
    }

    const uint8_t *frameData() const
    {
        return buffer;
    }

    uint8_t frameLength() const
    {
        return index;
    }

    void reset()
    {
        index = 0;
        frameReady = false;
    }

private:
    uint8_t buffer[64];
    uint8_t index;
    bool frameReady;
};
```

这个类只演示入门思路。实际项目可以继续加入长度字段、CRC、超时计数和功能码分发。

## 5. 常见错误

- 类里直接操作硬件寄存器，导致协议解析和底层驱动强耦合。
- 构造函数里做复杂硬件初始化，初始化顺序难排查。
- 使用动态内存保存帧，单片机上容易带来碎片和不可控失败。
- 没有 `reset()`，错帧后解析器无法恢复。
- 只封装了发送，不封装接收状态机，项目仍然难维护。

## 6. 调试方法

调试协议类时，先不接真实硬件。用固定字节数组逐个调用 `input()`，确认解析状态正确。

| 测试项 | 输入 | 期望结果 |
|---|---|---|
| 正常帧 | `$OK#` | `hasFrame()` 为真 |
| 非法帧头 | `ABC#` | 不产生完整帧 |
| 超长帧 | 超过缓冲区长度 | 返回错误并复位 |
| 连续帧 | `$A#$B#` | 处理第一帧后复位，再处理第二帧 |

如果接入 RS485 或真实串口，仍要保存 TX/RX 原始字节。硬件接线、端子、波特率和方向控制必须回到数据手册、原理图和实测结果确认。

## 7. 面试常问问题

1. 问：为什么要把协议解析封装成类？
   答：可以把缓冲区、解析状态、校验和复位逻辑集中管理，外部只通过清晰接口输入字节和获取完整帧。

2. 问：协议类应该直接收发串口吗？
   答：不建议。协议类负责解释字节含义，串口收发应放在驱动层或设备类中，避免耦合。

3. 问：嵌入式 C++ 协议类为什么要避免动态内存？
   答：动态内存可能造成碎片和不可预测失败，固定缓冲区更容易控制资源和调试。

4. 问：错帧后怎么办？
   答：协议类应提供复位机制，丢弃当前错误数据，回到等待帧头状态。

5. 问：协议类和 Modbus RTU 有什么关系？
   答：Modbus RTU 也可以封装成协议类，内部处理地址码、功能码、数据区、CRC 和异常响应。

## 8. 简历表达方式

> 使用 C++ 封装串口协议解析类，将接收缓冲区、解析状态、完整帧判断和复位逻辑集中管理，为 RS485 自定义协议和 Modbus RTU 解析提供清晰接口。

## 10. 小结

协议类设计的重点是边界。它不负责真实硬件接线，不负责业务动作，只负责把字节流解析成可处理的帧。掌握这个思路后，C++ 在嵌入式项目中就不再只是语法，而是服务于协议清晰、调试清晰和面试表达清晰。
