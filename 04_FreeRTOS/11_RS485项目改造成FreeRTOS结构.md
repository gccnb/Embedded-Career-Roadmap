# RS485 项目改造成 FreeRTOS 结构

## 1. 本节要解决什么问题

裸机 RS485/Modbus 项目一开始可以写在 `while (1)` 里：收到数据就解析，解析完就回包，再顺手采集传感器、刷新状态灯。项目小的时候能跑，但功能一多就会变乱。

本节要解决的问题是：如何把一个裸机 RS485/Modbus 项目改造成 FreeRTOS 多任务结构，让通信、解析、业务处理和日志记录各自负责一件事。

## 2. 基本概念

FreeRTOS 改造不是“把每个函数都变成任务”。任务太多会增加调度和同步复杂度。正确思路是按职责拆分：

| 模块 | 裸机写法 | FreeRTOS 写法 |
| --- | --- | --- |
| 串口接收 | 中断写缓冲区，主循环轮询 | 中断收字节，信号量通知通信任务 |
| 协议解析 | 主循环里判断完整帧 | 通信任务解析 Modbus 帧 |
| 业务处理 | 解析后直接改变量 | 通过队列把命令发给业务任务 |
| 日志记录 | 到处 printf | 日志任务统一保存 TX/RX 和错误 |
| 周期采集 | 主循环计数延时 | 采集任务周期运行 |

任务之间不要随便共享全局变量。能用队列传消息就用队列，必须共享资源时再考虑互斥锁。

## 3. 工程用途

在一个抽象工业控制项目里，下位机可能同时做：

- 接收 Qt 上位机的 Modbus 请求；
- 控制 RS485_EN/DE/RE 方向；
- 解析 03/06 功能码；
- 更新模拟寄存器表；
- 周期采集传感器；
- 保存通信错误统计；
- 刷新 LED 或报警状态。

如果全写在一个主循环里，很容易出现通信阻塞、采样不准、日志打印打断时序等问题。FreeRTOS 的价值是让每个任务只负责自己的节奏。

涉及真实传感器、驱动器、控制卡、端子和接线时，任务周期、通信参数和 IO 定义必须以数据手册、原理图和实测结果为准，不要凭经验编造。

## 4. 简单代码或伪代码

一个适合初学者的任务划分如下：

```text
USART/RS485 中断
    -> 释放 rxSemaphore
CommTask
    -> 取完整帧，校验 CRC，解析功能码
    -> 把读写请求放入 commandQueue
AppTask
    -> 更新寄存器表或业务状态
    -> 生成响应内容
LogTask
    -> 保存 TX/RX 原始帧、超时、CRC 错误
```

简化伪代码：

```c
void USART_IRQHandler(void)
{
    uart_read_to_buffer();
    if (frame_maybe_complete()) {
        xSemaphoreGiveFromISR(rxSemaphore, 0);
    }
}

void CommTask(void *arg)
{
    for (;;) {
        if (xSemaphoreTake(rxSemaphore, portMAX_DELAY) == pdTRUE) {
            if (modbus_check_crc(rxBuffer, rxLength)) {
                xQueueSend(commandQueue, &cmd, 0);
            } else {
                log_error(LOG_CRC_ERROR);
            }
        }
    }
}

void AppTask(void *arg)
{
    for (;;) {
        if (xQueueReceive(commandQueue, &cmd, portMAX_DELAY) == pdTRUE) {
            process_command_and_build_response(&cmd);
        }
    }
}
```

真实项目要注意 ISR API 和普通任务 API 不同，比如中断里要使用 `FromISR` 版本。

## 5. 常见错误

- 任务拆太多，每个任务职责反而不清楚。
- 串口中断里直接做 Modbus 解析，导致中断执行过长。
- 通信任务优先级太低，接收处理不及时。
- 日志打印和串口通信抢同一个外设，没有互斥保护。
- 多任务直接读写寄存器表，没有明确所有权。
- 队列长度太短，偶发丢命令却没有统计。

面试时如果你说“我用了 FreeRTOS”，面试官往往会追问任务怎么分、优先级怎么定、任务之间怎么通信。不要只停在“创建了几个任务”。

## 6. 调试方法

调试 FreeRTOS 版 RS485 项目，要多看“任务状态”和“通信日志”：

1. 给每个任务加心跳计数，确认任务都在运行。
2. 统计 `rxSemaphore` 触发次数和通信任务处理次数。
3. 记录 `commandQueue` 当前长度和发送失败次数。
4. 保存每帧 TX/RX 十六进制数据、CRC 结果、响应时间。
5. 检查任务栈剩余空间，避免运行一段时间后异常。
6. 暂时关闭日志任务，观察通信时序是否改善。

如果 RS485 通信异常，不要只怀疑 RTOS。仍要回到波特率、A/B 线、方向控制、TC 标志位、终端电阻和设备手册。

## 7. 面试常问问题

1. 问：为什么要把 RS485 项目改成 FreeRTOS？
   答：功能变多后，通信、采集、控制、日志有不同节奏。RTOS 可以按职责拆任务，避免一个主循环里互相阻塞。

2. 问：通信任务优先级应该怎么考虑？
   答：通信接收通常不能太低，否则可能处理不及时；但也不能长时间占用 CPU。要结合波特率、帧频率、业务实时性来定。

3. 问：中断和任务之间怎么同步？
   答：中断只接收数据或判断事件，然后用信号量、队列或任务通知唤醒通信任务，复杂解析放到任务里。

4. 问：寄存器表被多个任务访问怎么办？
   答：最好明确寄存器表由某个任务维护，其他任务通过队列请求；如果必须共享，要用互斥锁或临界区保护。

5. 问：FreeRTOS 项目如何定位偶发卡死？
   答：看任务心跳、栈剩余、队列阻塞、互斥锁占用、日志输出位置，再结合通信原始帧和错误统计。

## 8. 简历表达方式

> 将裸机 RS485/Modbus 通信程序改造成 FreeRTOS 多任务结构，拆分通信接收、协议解析、业务处理和日志任务，使用信号量和队列完成中断与任务同步，并记录 CRC 错误、超时和队列异常。

这句话比“熟悉 FreeRTOS”更具体，也更容易引出任务拆分和调试过程。

## 9. 小练习

1. 画出一个 RS485/Modbus 项目的 4 个任务：通信、业务、采集、日志。
2. 设计一个 `CommandMessage` 结构体，用于队列传递功能码和寄存器地址。
3. 思考通信任务和日志任务是否会抢同一个串口。
4. 给每个任务设计一个心跳变量和错误计数。
5. 把裸机串口接收流程改写成“中断 + 信号量 + 通信任务”。

## 10. 小结

FreeRTOS 改造的重点不是任务数量，而是职责清楚、同步明确、日志可查。RS485/Modbus 项目非常适合练这个能力，因为它天然包含中断、缓冲区、协议解析、方向控制、超时和错误统计。

真正能打动面试官的不是“我用过 FreeRTOS”，而是你能讲清楚任务为什么这样拆、队列传什么、信号量怎么用、出现 CRC 错或超时时怎么定位。
