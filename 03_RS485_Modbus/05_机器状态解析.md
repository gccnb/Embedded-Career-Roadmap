# 机器状态解析

## 1. 本节要解决什么问题

本节要解决的问题是：通信协议收到的数据，如何转换成程序能理解的设备状态。

串口或 Modbus 收到一帧数据后，不能只停留在“收到了几个字节”。工程项目里更重要的是：这些字节表示设备空闲、运行、报警还是急停？某一位表示什么错误？状态变化后程序应该做什么？Qt 上位机应该怎么显示？

机器状态解析是协议项目和控制项目之间的桥梁。它把底层通信数据转换成状态字、错误码、状态机事件，再驱动控制逻辑、日志记录和上位机显示。

## 2. 基本概念

机器状态可以用状态枚举、状态字或错误码表示。

常见方式如下：

| 表示方式 | 示例 | 适合场景 |
|---|---|---|
| 状态枚举 | `IDLE`、`RUNNING`、`ALARM` | 主状态清晰、状态数量不多 |
| 状态字 | bit0 运行、bit1 报警、bit2 急停 | 多个状态可同时存在 |
| 错误码 | `0x01` 过压、`0x02` 超时 | 故障类型需要明确记录 |
| 状态机 | 空闲 -> 运行 -> 完成/报警 | 控制流程有明确转移关系 |

例如一个 16 位状态字可以这样定义：

| 位 | 含义 |
|---:|---|
| bit0 | 设备运行中 |
| bit1 | 有报警 |
| bit2 | 通信超时 |
| bit3 | 参数未配置 |
| bit4 | 动作完成 |

这只是教学定义，不代表真实设备状态字。真实设备的状态位、错误码、报警含义必须来自数据手册、协议文档、原理图或实测验证，不能凭经验编造。

## 3. 工程用途

状态解析常出现在以下场景：

- 单片机解析上位机命令后更新本机状态；
- Qt 上位机读取 Modbus 寄存器后显示运行、报警、完成状态；
- FreeRTOS 项目中通信任务把状态消息发给控制任务；
- 机器视觉控制系统抽象案例中，根据识别结果和执行模块响应更新流程状态。

在求职项目里，状态解析能明显提高项目质量。因为它说明你不是只会收发字节，而是能把通信数据变成控制逻辑和界面显示。

典型链路：

```text
RS485/Modbus 接收帧
-> 校验 CRC
-> 解析寄存器或状态字
-> 更新设备状态结构体
-> 触发控制逻辑或上位机显示
-> 记录状态变化日志
```

## 4. 简单代码或伪代码

下面示例演示如何解析一个 16 位状态字。

```c
#include <stdint.h>

#define STATUS_RUNNING      (1u << 0)
#define STATUS_ALARM        (1u << 1)
#define STATUS_COMM_TIMEOUT (1u << 2)
#define STATUS_NOT_CONFIG   (1u << 3)
#define STATUS_DONE         (1u << 4)

typedef enum {
    MACHINE_IDLE = 0,
    MACHINE_RUNNING,
    MACHINE_DONE,
    MACHINE_ALARM
} MachineState;

typedef struct {
    uint16_t rawStatus;
    uint8_t isRunning;
    uint8_t hasAlarm;
    uint8_t commTimeout;
    MachineState state;
} MachineStatus;

void parse_machine_status(uint16_t statusWord, MachineStatus *out)
{
    out->rawStatus = statusWord;
    out->isRunning = (statusWord & STATUS_RUNNING) ? 1u : 0u;
    out->hasAlarm = (statusWord & STATUS_ALARM) ? 1u : 0u;
    out->commTimeout = (statusWord & STATUS_COMM_TIMEOUT) ? 1u : 0u;

    if (out->hasAlarm || out->commTimeout) {
        out->state = MACHINE_ALARM;
    } else if (statusWord & STATUS_DONE) {
        out->state = MACHINE_DONE;
    } else if (out->isRunning) {
        out->state = MACHINE_RUNNING;
    } else {
        out->state = MACHINE_IDLE;
    }
}
```

这段代码的重点是把原始状态字保留下来，同时解析出可读状态。保留 `rawStatus` 很重要，因为调试时要能回到原始数据，而不是只看转换后的枚举。

## 5. 常见错误

1. 不保留原始状态字。只保存解析结果，后续无法排查协议或位定义错误。
2. 位定义和协议文档不一致。比如把 bit1 当运行位，实际 bit1 是报警位。
3. 状态优先级不清。运行和报警同时出现时，不知道界面显示哪个。
4. 状态变化没有日志。设备从运行到报警，无法复盘是哪一帧触发。
5. 把状态解析和通信接收混在一起。接收层、解析层、业务层边界不清。
6. 编造真实设备状态位。公开学习项目只能使用抽象状态字和模拟错误码。

## 6. 调试方法

调试状态解析要同时看三类数据：原始帧、原始状态字、解析后的状态。

| 调试项 | 示例 | 作用 |
|---|---|---|
| 原始帧 | `01 03 02 00 03 ...` | 确认通信数据是否正确 |
| 原始状态字 | `0x0003` | 确认位数据来源 |
| 解析结果 | `running=1 alarm=1` | 确认代码位运算是否正确 |
| 状态机结果 | `MACHINE_ALARM` | 确认业务优先级是否正确 |

建议日志格式：

```text
[16:20:01.100] RX 01 03 02 00 03 XX XX
[16:20:01.101] STATUS raw=0x0003 running=1 alarm=1 timeout=0
[16:20:01.102] STATE MACHINE_ALARM
```

如果 Qt 上位机显示状态不对，不要直接改 UI。先确认下位机返回的原始帧，再确认寄存器高低字节，再确认状态位定义，最后检查 UI 显示逻辑。

## 7. 面试常问问题

1. 问：什么是状态字？
   答：状态字通常是一个 8 位、16 位或 32 位数据，用不同 bit 表示不同状态，比如运行、报警、完成、超时等。

2. 问：为什么状态解析要保留原始值？
   答：原始值是调试证据。解析结果错了时，可以根据原始值检查协议、字节序、位定义和代码逻辑。

3. 问：报警和运行状态同时出现怎么办？
   答：要定义状态优先级。一般报警优先级高于运行显示，业务逻辑应先进入异常处理。

4. 问：状态解析和状态机有什么关系？
   答：状态解析把通信数据转换成事件或状态；状态机根据这些事件决定系统从空闲、运行、完成、报警之间如何转移。

5. 问：Modbus 项目中状态通常怎么传？
   答：常见做法是用保持寄存器或输入寄存器传状态字、错误码、计数值等。具体地址和位定义必须以协议文档为准。

## 8. 简历表达方式

> 实现设备状态字解析逻辑，将通信帧中的原始状态寄存器转换为运行、完成、报警、通信超时等可读状态，并保留原始状态字和 TX/RX 日志用于问题定位。

如果结合 Qt 上位机，可以写：

> 在 Qt 上位机中显示状态字解析结果和状态变化日志，支持根据原始帧复盘通信和状态切换问题。

## 9. 小练习

1. 设计一个 16 位状态字，至少包含运行、报警、急停、完成、通信超时 5 个状态位。
2. 写一个函数，把状态字解析成结构体，并保留原始状态字。
3. 设计状态优先级：报警、急停、运行、完成、空闲，说明为什么这样排。
4. 给 Qt 上位机设计一个状态显示表格：原始值、运行、报警、超时、当前状态。

## 10. 小结

机器状态解析把通信数据变成工程项目能使用的状态信息。它要求你既理解协议帧和寄存器，也理解位运算、状态优先级、日志复盘和上位机显示。掌握这部分后，RS485/Modbus 项目会从“收发数据”升级为“能解释设备状态和控制流程”的项目。
